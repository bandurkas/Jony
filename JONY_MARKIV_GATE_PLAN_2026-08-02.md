# Jony: живой markIv вместо realized-vol для входных гейтов — план

> Не начатая research-ветка. Ничего не закодировано в живом коде. Продолжать
> в новой сессии с раздела "Что делать в следующей сессии" внизу.

## Идея и почему она интересна

Текущий вход (`_evaluate_side` в `research/jony_core.py`, зеркалит
`core/strategy.py`) фильтрует по `vol_high`/`vol_pctile` — перцентиль
**реализованной** волатильности (`rv1h_native`, realized vol цены за 24ч)
относительно своей же истории за `HIST=240` часов. Это КОСВЕННЫЙ прокси
экономического тезиса стратегии (VRP — variance risk premium): "продавать
премию когда она дорогая относительно того, что реально реализуется".
Realized vol сейчас высокая — не то же самое, что "рынок продаёт премию
дорого прямо сейчас": движок никогда не смотрит на реальный `markIv` при
принятии решения о входе — только на прошлое ценовое поведение.

Найдено в этой сессии (§ sigma-калибровка): реальный `markIv` и модельная
`rv1h_native` коррелируют, но слабо (R²=0.40) и с систематическим
расхождением. Значит вход "по realized vol" и вход "по реальной цене
премии, которую рынок готов дать" — не одно и то же, и разница может быть
именно тем экономическим эджем, который стратегия пытается поймать, но
сейчас ловит через шумный прокси.

## Ключевой блокер — почему это НЕ обычный research-цикл этого проекта

Всё остальное тюнилось на 2-летней истории klines (`research/fetch_bybit_klines.py`).
Для **опционного IV** такой истории физически не существует:
- Bybit не отдаёт исторические klines по опционам (`category=option` —
  `retCode:10001 invalid category`, проверено в этой сессии).
- Единственный источник реального IV — свой же коллектор, который начал
  писать данные только 2026-06-19 (Boba1's `iv_collector.py`,
  `research/fresh_data/iv_history_eth.jsonl`, 6272 записей).
- Этот коллектор берёт **ближайший срок экспирации (6-36ч)**, а Jony торгует
  **недельными (168ч)** — прямо другой инструмент (см. §7 хендоффа,
  `SESSION_HANDOFF_2026-08-02.md`) — экстраполировать нельзя, это уже
  проверялось и отклонялось для похожего вопроса (BTC-коллектор).

**Вывод**: бэктест этой идеи на 2 годах истории невозможен в принципе.
Флоу "идея → бэктест → ревью → тюнинг" для ЭТОГО рычага превращается в
"идея → **начать собирать реальные данные** → ждать несколько недель →
анализ → тюнинг". Это единственный рычаг в проекте с таким свойством —
дальше можно action-item сделать уже сейчас (запустить коллектор), а
решение принимать через несколько недель.

## Дизайн коллектора (не задеплоен, план)

Зеркалит `iv_collector.py` Boba1 (stdlib-only, cron, append-only JSONL,
никак не трогает торговый код — тот же паттерн изоляции):

- Новый файл `research/iv_collector_weekly.py` в репо Jony.
- Каждые 10 мин: для ETH и BTC, для C и P — контракт **ближайший к 168ч**
  (не ближайший вообще), через ту же логику что `pick_atm_option`.
- **BTC PUT тоже включить** (даже раз BTC сейчас торгует только CALL) — это
  тот же самый ход, который параллельно нужен для отдельного неисследованного
  рычага "BTC PUT" (см. предыдущий ответ в чате) — один коллектор, два
  будущих исследования, дёшево добавить сейчас.
- Пишет: `ts_ms`, `spot`, `rv1h_native` (та же формула что в движке —
  переиспользовать `rolling_realized_vol`, НЕ `rv_168h` Boba1, чтобы точно
  сравнивать с движком) для каждой монеты, плюс `markIv`/`bid`/`ask`/`markPrice`/
  `dte_h`/greeks для ATM C и P.
- Хранить в `research/fresh_data/iv_history_weekly.jsonl` (gitignored, как
  остальные fresh_data — не коммитить сами данные, только код коллектора).
- Деплой: cron на VPS3, НЕ внутри Jony-контейнера (та же изоляция что у
  Boba1 — сбой коллектора не должен уметь тронуть торговый луп).

**Риск**: минимальный — read-only, ничего не пишет в БД бота, ничего не
меняет в решениях. НЕ требует полного цикла architecture→code→review→tests
→deploy как у смены стратегии — но всё равно нужна проверка "не молчит ли
он тихо" (урок Tyagach §17.1: немой сбой сбора данных может остаться
незамеченным неделями) — минимум: первый запуск вручную + проверка что
файл растёт после первого cron-тика.

## Два варианта самого гейта (решать после накопления данных)

1. **IV-level gate** (проще, прямая замена): вместо/вместе с
   `vol_high` (перцентиль `rv1h_native`) — перцентиль реального `markIv`
   в своей же истории. Минимальное изменение механизма, легче сравнивать
   с текущим гейтом.
2. **VRP-spread gate** (ближе к экономическому тезису, сложнее): входить
   только если `markIv` заметно выше ожидаемой будущей realized vol —
   требует модели ожидания будущей vol (сама по себе нетривиальная задача,
   не просто перцентиль).

Рекомендация: начинать с (1), она напрямую сравнима с существующим
`vol_threshold` механизмом на тех же данных, когда они накопятся.

## Что делать в следующей сессии

1. Прочитать этот файл целиком.
2. Проверить, стоит ли коллектор (задеплоен в этой сессии или ещё нет —
   см. ниже) и сколько данных накопилось (`wc -l
   research/fresh_data/iv_history_weekly.jsonl` на VPS3 или локально после
   копирования).
3. Если данных мало (<2-3 недели) — рано для анализа, только проверить что
   коллектор жив и не молчит.
4. Если данных достаточно — построить IV-level gate (вариант 1 выше),
   сравнить с текущим `vol_threshold` на РЕАЛЬНОМ (не бэктестовом) окне —
   это будет первый в проекте гейт, валидируемый только вперёд, а не на
   2-летней истории.
5. **Параллельная возможность** (не забыть): та же логика "начать собирать
   сейчас, анализировать через недели" применима к отдельной незакрытой
   находке — реальный per-position mark path для TP2/SL (см. чат от
   2026-08-02, "живой vs бэктест" расследование) — можно задеплоить оба
   коллектора одним раундом, если решим двигаться.
